# I5: scheduled live runs on Drive, OneDrive and MEGA — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The I3 rig's `bridge`, `direct` and `shared` checks run on a schedule against the real Google Drive, OneDrive and MEGA test accounts, each run inside a sandbox folder of its own that it removes again, leaving every account as it found it, with the sign-in tokens kept alive by the runs themselves.

**Architecture:** Three layers, all in xtask. (1) `cargo xtask-live interop live-auth <target>`, run once by the owner on their own machine, signs in through Bunko's own OAuth code (or reads the saved MEGA session), checks the result with one harmless read and stores it as a GitHub Actions secret through `gh secret set`, the value on stdin. (2) `cargo xtask interop rig … --live`, run by a scheduled workflow, reads those secrets from the environment, refreshes once, writes a rotated OneDrive token straight back, hands Bunko a credentials file and the reader an access token, and points both at a top-level sandbox folder `bunko-interop-<run-id>` instead of `mokuro-reader`. (3) A sandbox guard that snapshots the account before the run, refuses any write outside the sandbox, deletes the sandbox at the end and diffs against the snapshot. The Playwright specs stay as they are: a live stand-in for cloudsim's `/_sim/` read endpoints (scoped to the sandbox) answers what they ask of the cloud, and specs that need simulator faults are skipped on live runs.

**Tech Stack:** Rust 2024 (xtask with a new non-default `live` feature: `bunko-remote` with `oauth`, `bunko-mega`, `tokio`, `reqwest`, `rpassword`, all already in Cargo.lock), the `gh` CLI, GitHub Actions. Reader: TypeScript (one test-only hook).

**Spec:** `docs/design/interop-testing.md` §7.2 (live runs), §7.3 (MEGA bandwidth), §9 (CI wiring), §10 (I5 row), §11 (Google refresh-token lifetime).

## Findings that shape the design (verified 2026-11-15)

- **Bunko's library root is one folder name, not a path.** `storage.library.folder` (default `mokuro-reader`) is passed to `Backend::locate_roots(name)`: Drive finds every folder of that exact name anywhere the app can see (`gdrive/mod.rs:1201`), OneDrive only `/me/drive/root:/{name}` with `check_name` refusing a separator (`onedrive/mod.rs:1167`), MEGA every folder of that name outside the rubbish bin, Cloud Drive children first (`mega/mod.rs:1111`). So Bunko cannot be pointed at `mokuro-reader/bunko-interop/<run-id>`; it can be pointed at a top-level folder with a unique name. The store id includes the folder (`store_id(provider, pairing, account, folder)`), so a sandbox store never shares state with a `mokuro-reader` store.
- **The reader's root is a constant per provider** (`'mokuro-reader'` in `onedrive/constants.ts`, `google-drive/drive-files-cache.ts`, `mega/mega-provider.ts`, `core/providers/*-core.ts`, `webdav-core.ts`), with no override. Its test hooks (`util/sync/cloud-test-hooks.ts`, on only in the `test` and `interop` modes, folded out of production builds and checked by `scripts/check-no-test-hooks.mjs`) already take `__mokuroInteropConfig` v1 with API bases, a Google access token (`{access_token, expires_in}`) and a OneDrive access token, and install the gapi REST shim on `gapiShim`. They take no MEGA session: the rig signs the reader in to cloudsim's MEGA with an email and password (`rig/browser.rs:252`).
- **OAuth in Bunko:** `LoopbackFlow::start(&client)` → `(url, Pending)`, `Pending::wait()` → `Tokens` (loopback + PKCE, `http://127.0.0.1:<port>/` for Google's Desktop clients, `http://localhost:<port>/bunko` for Microsoft, which personal accounts need: the device flow is AADSTS70002 for consumers). `refresh(&client, rt)` returns the rotated refresh token for Microsoft and the old one for Google; `AuthError::InvalidGrant` is a dead grant. `OAuthClient.token_url` is a plain field, so cloudsim's `/oauth/{google,microsoft}/token` stands in. Google's secret is compile-time (`BUNKO_GOOGLE_BETA_DESKTOP_SECRET`, `clients.rs`); a client without one at Google's real token URL refuses to refresh (`lacks_google_secret`). The custom override (`storage.library.oauth.google.client_id`/`client_secret`) gives a build without the secret the same client at run time.
- **drive.file is per Cloud project** (2026-10-12 spike): a token from Bunko's beta Desktop client sees exactly the files the beta project's reader created, so a token minted from Bunko's refresh token works for the reader's Drive calls too. The reader's own web client is not needed.
- **MEGA:** the saved session is `credentials.json` in Bunko's `cloud/` layout (`{version, stores: {<id>: {provider: "mega", account_id, account_label, mega_session}}}`, unsealed), read by `CredentialStore`. `bunko_mega::Client::resume(cfg, blob)` validates it with one `us` call; `user_info()` (`ug`) and `storage_quota()` (`uq`) are the cheap reads. `locate_roots` on MEGA fetches the whole node tree (`f`, metadata only, no transfer quota), the old ~1,800-volume library included; nothing downloads it.
- **The rig's specs read the cloud through cloudsim's control API** (`fixtures.mjs` `sim()`): `/_sim/tree`, `/_sim/content`, `/_sim/node` (seeding, `dup-roots.mjs`), `/_sim/fault` (`direct/faults`), `/_sim/violations`, `/_sim/token`.
- **Schedules run the default branch's workflow file** (`main`); `interop-nightly.yml` handles that with a ref matrix. A scheduled live run of 0.8 checks out `0.8/remote-storage` the same way.
- The develop/beta project's OAuth consent screen was already "In production" on 2026-10-12 (owner session notes), so its refresh tokens do not expire after 7 days; the owner confirms it once (owner setup, step 1).

## Decisions

1. **Sandbox root: a top-level folder `bunko-interop-<run-id>`, never under `mokuro-reader/`.** Bunko gets `storage.library.folder: bunko-interop-<run-id>`; the reader gets the same name through a new test-only hook (Task 5). `<run-id>` is `<UTC yyyymmddThhmmss>-<github run id or "local">`, so it is unique and sorts by age. The runner refuses a folder name that is not `bunko-interop-` followed by a run id, compared case-insensitively, so it can never be `mokuro-reader`. The spec's "under `mokuro-reader/`" changes to this (§7.2 updated).
2. **Snapshot scope:** the account's top level (name, id, kind, size, modified time, hash) and the direct children of every top-level `mokuro-reader` folder (same fields): enough to see a stray write into the real library or a pre-existing JSON file edited, without listing the library itself. Plus the rubbish/trash entries the app can see (Drive `trashed=true` under drive.file, MEGA's rubbish bin children). OneDrive's recycle bin has no Graph listing for personal accounts: not diffed, and the run's own deletes land there and age out after 30 days (documented, not a failure).
3. **Cleanup:** the runner deletes the sandbox folder permanently at the end, pass or fail (Drive `files.delete`, MEGA `d`, OneDrive `DELETE` + recycle-bin residue as above), then deletes permanently whatever the run moved to the trash/rubbish (entries new since the snapshot whose path started in the sandbox). Then the diff: any difference outside the sandbox fails the run, naming the entry (never its content). A run that finds a `bunko-interop-*` folder older than 48 hours (a crashed run) deletes it first and says so; one younger than that fails the run (another run may be live; the workflow's concurrency group should make that impossible).
4. **How the reader gets tokens:** the runner refreshes once per provider per run and passes the access token in `__mokuroInteropConfig.tokens` (`google: {access_token, expires_in}`, `onedrive: <token>`), with the real API bases (`bases.driveApi: https://www.googleapis.com`, `gapiShim: true`, so no Google Identity Services and no apis.google.com script). An hour covers a run; a run that needs longer refreshes and re-injects through `__mokuroCloudTestHooks.setCloudTestToken`. MEGA: the reader gets the same session Bunko uses, converted to megajs's `Storage.toJSON` shape (Task 5: a `tokens.mega` hook and a `bunko-mega` accessor for the master key after `resume`), so no MEGA password is ever stored. Neither party calls MEGA's logout on that session (`sml` would end it for both); the reader's disconnect in a live run is skipped.
5. **Token upkeep.** Drive: refresh tokens of a production-status project do not expire on a timer; a dead one (`invalid_grant`: revoked, password change, six months unused) fails the run with "the Drive sign-in is no longer valid: run `cargo xtask-live interop live-auth gdrive` again". OneDrive: rotated on every refresh. The runner stores the new one the moment it gets it (before Bunko starts), then at teardown reads Bunko's `credentials.json` for the newest (Bunko rotates again during the run) and stores that. The write uses Task 1's secret writer, `GH_TOKEN` = `BUNKO_LIVE_SECRETS_TOKEN`. In Actions, every token the runner obtains is masked first (`::add-mask::`), and nothing prints one.
6. **Schedule:** Drive and OneDrive nightly at 05:41 UTC (after `interop-nightly` at 03:17 has rebuilt `nightly-0.8`), MEGA weekly (Sunday 06:23 UTC), `workflow_dispatch` with a provider choice for a pre-release check. One concurrency group per provider, never cancelling a run in progress (a cancelled OneDrive run would lose its rotated token; a cancelled run of any provider would skip cleanup).
7. **MEGA quota (§7.3):** a ~5 MB fixture (two short volumes); the runner reads `uq` with transfer fields first and skips the run ("skipped: transfer quota") when less than 3× the fixture is left; the first over-quota answer (`EOVERQUOTA`, HTTP 509, `-17` on a download) stops the run, cleanup still runs (deletes cost no transfer), and the run reports skipped. Skipped is a warning; two skipped runs in a row fail (the previous run's result is read from its `live-mega` artifact with `gh run download`). Bytes moved per party per run go into the results file.
8. **Builds:** the live job uses the `nightly-0.8` testing server (no Google secret in it) with the Google client given as the custom override at run time (`storage.library.oauth.google`, the beta Desktop client id and `BUNKO_GOOGLE_BETA_DESKTOP_SECRET`), the reader built as `rig-build` builds it, and xtask built with `--features live`.

## Global Constraints

- Nothing in this plan's tests contacts a real cloud or GitHub: cloudsim stands in for the providers and a fake `gh` script for GitHub. Only the owner runs `live-auth` for real, and only the scheduled workflow runs `--live`.
- No token, session, client secret or password is ever printed, logged, put in a command line or written to disk by the sign-in commands. The values reach `gh` on stdin. The runner writes Bunko's `credentials.json` and `config.yaml` only inside the run's own temporary data directory, mode 600, deleted at the end.
- No run reads, writes or deletes anything outside its sandbox folder except the snapshot reads of decision 2 and the trash entries of decision 3. No run downloads a byte of the old MEGA library.
- `live` is a non-default xtask feature: release jobs keep building xtask without `bunko-remote`. CI lints and tests the feature (`ci.yml`).
- No deployment, host or account is named anywhere (repo `CLAUDE.md`); no account email in code, docs, commits or logs. The sign-in command shows the account it signed in to on the owner's terminal only.
- Bunko: `cargo fmt`, `cargo +1.99.1 clippy -p xtask --all-targets --offline -- -D warnings` (with and without `--features live`), `cargo test -p xtask --offline` (with and without `--features live`), with `XDG_CONFIG_HOME` and `XDG_DATA_HOME` pointed at a scratch directory. Don't commit until the task's tests pass. Commit messages end with the session's attribution line.

## Review Focus

1. **A token in output:** every path of the sign-in commands, success and failure, prints no token, session or client secret (sentinel tests in Task 1; the runner's logs in Task 2).
2. **A write outside the sandbox:** the guard refuses it before the request is sent, and the diff catches anything the guard cannot see (a write by the reader). Pinned in Task 3.
3. **A lost OneDrive token:** a run that fails anywhere after its first refresh still stores the newest refresh token. Pinned in Task 2 (cloudsim rotates like Microsoft).
4. **MEGA quota:** a run never downloads more than the fixture once, and stops at the first over-quota answer with cleanup intact. Pinned in Task 6 with cloudsim's MEGA quota knob.
5. **The old MEGA library:** no command downloads, moves, renames or deletes a node under the account's `mokuro-reader/`. Pinned by the guard's tests in Task 3.
