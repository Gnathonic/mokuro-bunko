# I2: cloudsim, the shared cloud simulator — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One HTTP server that plays Google Drive v3, Microsoft Graph (OneDrive) and MEGA, with a control API for tokens, faults, seeding and accounting. Bunko's mock tests run on it, a full Bunko server can be pointed at it, and the reader's provider code passes its provider suite against it.

**Architecture:** A new crate `bunko-cloudsim` (library + binary). The library form starts in-process on `127.0.0.1:0` for Rust tests; the binary serves the same router for the reader and for I3's rig. Drive and OneDrive are lifted out of `crates/bunko-remote/tests/{gdrive,onedrive}_mock.rs`; MEGA stays in `bunko-mega`'s `mock` module (it needs the crate's crypto internals) and is mounted under a prefix. Each provider lives under its own path prefix, so one port serves all three. State is per (provider, account); a token maps to its account.

**Tech Stack:** Rust 2024: axum 0.8, tokio, parking_lot, serde_json, base64, md-5, sha2 (all already in Cargo.lock; no new crates). Reader: TypeScript, Vitest (jsdom), megajs 1.3.9 (`gateway` option, `types/es.d.ts:171`).

**Spec:** `docs/design/interop-testing.md` §6 (cloudsim), §10 (I2 row), §11 (hooks must not ship).

## Findings that shape the design (verified 2026-10-28)

- Both Bunko mocks are axum 0.8 fallback handlers over `Arc<Mutex<St>>`, started in-process; tests change knobs by locking the state (`e.mock.0.lock().page_size = 2`). Drive: mock at `gdrive_mock.rs:28–780`, helpers 782–921, 15 tests. OneDrive: mock at `onedrive_mock.rs:32–871`, helpers 873–1038, 17 tests.
- The handlers check client behaviour with `assert!`/`panic!` (Drive lines 374, 418, 421, 481, 534, 596, 610, 653; OneDrive 430, 497, 510, 516, 582, 629, 656, 662–663, 699–708). A standalone server can't panic per request: these become 400 answers plus a recorded violation.
- Neither mock counts Drive quota units; Bunko counts them client-side (`gdrive::api::units`).
- MEGA mock: `crates/bunko-mega/src/mock.rs`, feature `mock`, axum routes `/cs`, `/sc`, `/wait/{sn}`, `/dl/{h}/{range}`, `/ul/{id}/{offset}`, real crypto, `pub async fn start() -> MockMega`. Users: `bunko-mega/tests/client.rs` (8), `bunko-remote/tests/mega_mock.rs` (10), `mega_scale.rs` (2, ignored).
- Driver seams: `GDriveConfig.api_base` (default `https://www.googleapis.com`; uploads use `{api_base}/upload/...`), `OneDriveConfig.api_base` (default `https://graph.microsoft.com/v1.0`), `bunko_mega::ClientConfig.api_origin` (default `https://g.api.mega.co.nz/`). Tokens: `TokenSourceDyn`, `RefreshingToken` over `OAuthClient { token_url, .. }`.
- A full server builds its stores in `bunko-server/src/storage/mod.rs` (`open_library_store` 702; Drive 798–808, OneDrive 809–819, MEGA 823–832; `token_source()` 1150) and in the connect probe (`storage/connect.rs` 450/459/468, MEGA login at 513 with the default origin). `mokuro-bunko` has no `testing` feature; `bunko-server`'s `testing` feature enables `bunko-remote/testing` (FakeBackend).
- Reader: Drive goes through `gapi.client.drive.files.*` loaded from `apis.google.com`, with XHR for media download (`api-client.ts:227`) and multipart upload (`:274`) and fetch in `core/providers/google-drive-core.ts` (14, 30, 86, 87). A base URL alone cannot redirect `gapi`, so tests install a small REST shim in place of `gapi.client.drive.files`. OneDrive: `GRAPH_BASE_URL` (`onedrive/constants.ts:6`) copied into module-level `BASE` in `graph-client.ts:5` and `onedrive-core.ts:7`; tokens via `onedriveTokenManager.getAccessToken()`. MEGA: `new Storage({...})` at `mega-provider.ts:377`, `Storage.fromJSON` at `:447`, worker at `core/providers/mega-core.ts:55, 84`; megajs takes `gateway`. `util/cloud.ts:9` and `util/backup.ts:29` hold Drive addresses but appear unused.

## Global Constraints

- No new crates or npm dependencies.
- cloudsim never panics on a request: every client mistake is a 4xx answer plus an entry in `GET /_sim/violations`. Rust tests assert the violations list is empty at the end (a helper does it on drop).
- Path prefixes: Drive `{base}/google` (so `GDriveConfig.api_base = {base}/google`), OneDrive `{base}/graph/v1.0` with the pre-authenticated download, upload-session and copy-monitor URLs under `{base}/graph/`, MEGA `{base}/mega/`, OAuth token endpoints `{base}/oauth/google/token` and `{base}/oauth/microsoft/token`, control API `{base}/_sim/`.
- Every response carries permissive CORS (`Access-Control-Allow-Origin` echoing the request's `Origin`, or `*` when there is none; preflights answered with 204 allowing the requested method and headers; expose `Location, ETag, Range, Content-Range, Retry-After, X-Hashcash, Content-Length`), so browsers and jsdom's XHR can use it.
- Test-only Bunko settings (`MOKURO_TEST_CLOUD_*`) work only in a build with the `testing` feature; a build without it refuses to start when one is set, naming the variable.
- Reader hooks compile to nothing in production builds: guarded by `import.meta.env.MODE === 'test' || import.meta.env.VITE_CLOUD_TEST_HOOKS === '1'`, and a CI step greps the production bundle for the hook names.
- Bunko: `cargo fmt`, `CARGO_TARGET_DIR=target/clippy199 cargo +1.99.0 clippy --workspace --all-targets --offline -- -D warnings`, `TMPDIR=$HOME/.cache/bunko-live-tmp cargo test -p bunko-cloudsim -p bunko-remote -p bunko-mega -p bunko-server --offline`. Reader: `npx prettier --check .`, `npx eslint .`, `npm test -- --run`, `npm run build`.
- No real cloud is contacted by anything in this plan. No real credentials anywhere.
- No private deployment names in code, docs or commits. Don't commit until the task's tests pass. Commit messages end with the attribution line from the session.

## Review Focus

1. **Two accounts on one provider** (the M7 shared-folder flows need the reader and Bunko on the same account, and isolation from a second): a token for account A never sees account B's files. Pinned in Task 2.
2. **A refresh after revoke** returns `invalid_grant`, and an expired access token gives 401 while its refresh token still works. Pinned in Task 2.
3. **Concurrent requests from Bunko and the reader** on one account (the store is shared): the state lock is never held across an await, and resumable uploads from two clients don't mix. Pinned by a two-client upload test in Task 2.
4. **The reader's Drive `q` strings** (the Bunko mock's parser panicked on anything it didn't know): unknown query syntax is a 400 plus a violation naming the query, so a reader query the simulator can't answer shows up as a clear failure. Pinned in Task 6.
5. **A stray `MOKURO_TEST_CLOUD_*` on a production build** refuses to start. Pinned in Task 5.
