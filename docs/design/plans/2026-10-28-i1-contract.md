# I1: contract fixtures between Bunko and the reader — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bunko exports what the reader reads as normalized golden files; the reader's unit tests parse those files instead of hand-written ones; the reader records the requests it sends to Bunko, with the response fields it needs, and Bunko replays them. A deliberate field rename on either side fails the other side's tests.

**Architecture:** One shared seed (`interop/contract/seed.json`) describes the users and the library. `crates/bunko-server/tests/contract_export.rs` builds a full-stack in-process server from it (`app::Services` + `app::assemble`, the only setup that has the CORS, queue-file and WebDAV layers), drives every request in a fixed list, normalizes volatile values to typed sentinels and compares the result with `interop/contract/bunko/*.json` (`BUNKO_BLESS=1` rewrites them). The reader, on its own branch, reads those files from a Bunko checkout in its unit tests, and writes `interop/contract/reader/*.json` (compare, or `READER_BLESS=1` to rewrite) from tests that capture the requests its code builds. `contract_replay.rs` sends each recorded request to the seeded server and checks the reader's declared expectations.

**Tech Stack:** Rust 2024 (bunko-server integration tests: tokio, tower `oneshot`, serde_json, base64; no new crates). Reader: TypeScript, Vitest (jsdom), Node fs in test-only helpers.

**Spec:** `docs/design/interop-testing.md` §5 (contract fixtures), §9 (CI wiring), §10 (I1 row).

## Findings that adjust the spec (verified 2026-10-28; Task 6 writes them into §5)

- The reader (feat/cloud-bunko) never calls `/login/api/check`, `/api/nav/config`, `/api/stats`, `/queue/api/status` or the catalog list/series/config/ocr-status APIs. The contract covers what the reader reads; those stay out.
- What the reader reads: `GET /login/api/me`, `POST`/`DELETE /login/api/token`, `GET /catalog/api/manifest?series=&volume=`, `.mokuro-queue.json` (HTTP copy and cloud copy), `.mokuro-bunko.json`, `series.json`, `catalog.json`, PROPFIND (Depth 0 privileges, plus the listing the `webdav` library sends), PUT response headers (`X-Mokuro-Put`, `X-Mokuro-Upload`, `X-Mokuro-Size`, `X-Mokuro-Manifest`, `X-Mokuro-Recheck-After`) and the PUT failure verdict JSON.
- `done[]` and `truncated` exist only in the cloud copy of the queue document (`bunko_remote::status::cloud_queue_doc`), not in the HTTP-served `.mokuro-queue.json`.
- The lease marker's `state` is `active` or `released`. "Claiming" and "held" are both `active` in the file; the difference is whether the settle wait has passed.
- The 401 and 429 credential refusals carry no `Retry-After`; only WebDAV 503s do. The fixtures pin what Bunko sends today.
- Latin-1 Basic bytes get 401 "Invalid authorization header" on WebDAV. Current readers send UTF-8 (`basicAuthHeader`); the Latin-1 case is a hand-written legacy record.

## Global Constraints

- No new crates in Bunko; no new npm dependencies in the reader.
- Fixtures are byte-identical across runs and machines (Linux, macOS, Windows CI). Anything unstable is replaced by a typed sentinel: ISO times → `"2000-01-01T00:00:00Z"`, HTTP dates → `"Sat, 01 Jan 2000 00:00:00 GMT"`, epoch seconds → `946684800` (milliseconds → `946684800000`), ETags → `"\"etag\""`, tokens → `"<token>"`, UUID-shaped ids → `00000000-0000-4000-8000-00000000000N` numbered by first appearance, other ids → `"<id-N>"`, sha256 → 64 zeros only if the content itself is not deterministic. Sentinels keep the JSON type, so the reader's parsers accept them.
- The generated archives are deterministic (fixed zip timestamps), so sizes and hashes stay real where possible.
- Only stable fields are kept. Headers: only those the reader reads, plus the ones the spec names (`WWW-Authenticate`, `Retry-After`, CORS headers, `ETag` presence).
- Test passwords live in `seed.json` (they are test values for a throwaway in-process server). Never put a real credential anywhere.
- No private deployment names in code, docs or commits.
- Bunko: `cargo fmt`, `CARGO_TARGET_DIR=target/clippy199 cargo +1.99.0 clippy --workspace --all-targets --offline -- -D warnings`, and `TMPDIR=$HOME/.cache/bunko-live-tmp cargo test -p bunko-server --offline` pass. Reader: `npx prettier --check .`, `npx eslint .`, `npm test -- --run` pass.
- Don't commit until the task's tests pass. Commit messages end with the attribution line from the session.

## Review Focus

1. **A run on Windows or macOS producing different bytes** (path separators in hrefs, CRLF, map ordering): the export must sort keys and normalize line endings. Pinned by Task 2's "export twice, compare" unit test and by CI on all three OSes.
2. **A missing Bunko checkout in the reader** (a contributor without the Bunko repo): contract tests skip with one loud warning; with `BUNKO_CONTRACT_REQUIRED=1` (CI) they fail. Pinned in Task 4.
3. **Sentinel timestamps making the reader think a marker or queue is stale or fresh**: the reader's loader rebases sentinel times relative to a given `now`. Pinned by a marker-freshness test in Task 4.
4. **A non-ASCII series or volume name** (Japanese names are the norm): the seed includes one, and its hrefs and manifest URLs round-trip. Pinned in Tasks 2 and 4.
5. **CORS preflight from an origin that is not allowed**: no `Access-Control-Allow-Origin`, and the request never reaches the app. Pinned in Task 1.

### Task 3: the replay test (Bunko)

**Files:**
- Create: `crates/bunko-server/tests/contract_replay.rs`, `interop/contract/reader/legacy/basic-latin1.json`, `interop/contract/reader/legacy/basic-utf8-raw-header.json`

**Interfaces:**
- Consumes: `contract_support::build_server`, `seed.json`.
- Produces: the record format the reader writes in Task 5:
  ```json
  {
    "request": {"method": "POST", "path": "/login/api/token", "auth": "basic:reader",
                "headers": {"content-type": "application/json"}, "body": {}},
    "expect": {"status": [200, 201], "body_fields": ["token", "token_type", "expires_at"],
               "headers": ["etag"]}
  }
  ```
  `path` may contain seed names (percent-encoded the way the reader encodes them). `body_fields` are dot paths (`permissions.canWriteProgress`, `volumes.0.manifest`); each must exist and be non-null. `headers` must be present. An `auth` of `bearer:<user>` is satisfied by issuing a fresh token for that user before the request. A record with `"after": "<other record name>"` runs after that one (for `If-None-Match` chains; the stored ETag from the earlier answer replaces the `"\"etag\""` sentinel).

- [ ] Write the replay: load every `reader/*.json` and `reader/legacy/*.json`, run each against a fresh seeded server, and collect all failures before failing (one message listing every record that broke and why). Zero records under `reader/` (before Task 5 lands) is a pass with a printed note, not a failure.
