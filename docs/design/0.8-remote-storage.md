## M0 results (2026-10-12)

M0 tested what the design rests on, against real accounts.

- **`drive.file` is granted per Cloud project, not per OAuth client.** A brand-new Desktop client in the same project as the reader's web client listed everything that web client had uploaded: 7,339 files, 133 series, 2,245 `.cbz` and 2,242 `.mokuro`, plus `catalog.json`, `volume-data.json`, `profiles.json` and `goals.json`. It also uploaded a file, got a refresh token, and refreshed it.
- **Each reader deployment has its own Google Cloud project, and a Drive library belongs to the project that uploaded it.**
  - Mokuro Reader runs as two deployments, each with its own project: release (reader.mokuro.app) and beta.
  - A client in one project lists only files that project created, even inside a `mokuro-reader/` folder shared with the other project. The release client saw the beta library's folder but only its own 10 files in it.
  - Bunko therefore has to sign in with the project of the reader the user actually uses (D25).
- **Real accounts have several `mokuro-reader/` roots.** The test account had three folders by that exact name in My Drive. This confirms the merged-root rule (D5, §5.9).
- **Drive returns `sha256Checksum` and `md5Checksum`** for uploaded files.
- **Clients are provisioned.**
  - Google: Bunko "Desktop" (loopback + PKCE) and "TVs and Limited Input" (device flow) clients exist in the release, beta and local-dev projects.
  - Microsoft: the reader's single app registration now has a Mobile and desktop platform (`http://localhost`) and allows public client flows. A device-code request for `Files.ReadWrite offline_access User.Read` returned a code.
- **MEGA:** the `mega` crate 0.8.0 (MIT OR Apache-2.0) is the base. It lacks ranged download, hashcash and chunked upload, which M5 adds [prov-mega H].
- **Still open, owned by M3:** whether an unmodified reader lists files Bunko uploads (the reverse direction), and whether the TV client sees the reader's files.

## Decision register

Sections below refer to these as D1–D26.

| # | Topic | Decision |
|---|---|---|
| D1 | Seam | `LibraryStore` mirrors the ~15 `std::fs` primitives the code uses, over absolute `Path`. A process mount table dispatches by longest prefix. Content is committed through one explicit call, `publish(staged, dest, &WriteIntent)`, at the 7 existing tmp→rename sites. Each caller keeps its own listing semantics (lossy vs skip non-UTF-8, symlink handling). |
| D2 | Paths | Absolute `Path`. A RemoteStore root is a synthetic `<base>/cloud/<store>/library` that never exists on disk, so a stray `std::fs` call fails with `NotFound`. A clippy `disallowed-methods` gate enforces the shim in bunko-library, bunko-dav and bunko-server. Case folding stays in `PathCase`. |
| D3 | Version keys | Remote mtime = the provider timestamp **that the reader lists**, truncated to its granularity G, plus a salt `H(pid‖cver) mod G`. `Stamp`, `py_mtime`, the DB cache keys and the DAV ETag format are unchanged. Bunko never sets provider mtimes. |
| D4 | Main sidecar is model output | Owner rule (2026-10-12): the main `<Vol>.mokuro` is model output; human edits belong in alternate layers whose content shows they are not model generated. **Today's reader does not follow this yet:** its editor writes corrections into the primary row and re-uploads it as the main sidecar (reader `reader/edit/edit-persist.ts:8-11,26-61`, `util/sync/sidecar-backfill.ts:340-380`). It rebuilds every `.mokuro` it uploads from its DB (`util/mokuro-metadata.ts` `buildMokuroMetadata`), with no `ocr_engine` and no edit marker, so Bunko cannot tell stock mokuro output from a reader-corrected file. **Upgrade rule (M2, every store, its own CHANGELOG entry):** an outdated main sidecar is upgraded when its family is in `ocr.upgrade.replace`. Nothing is upgraded unless `ocr.upgrade.enabled` is on (default off). The default `replace` list is `mokuro-legacy` and `mokuro` (`bunko-core/src/config.rs:255-261`). An `unknown` family (neither `ocr_engine` nor `version`) is never upgraded. One proven to be Bunko's own bytes is replaced with no copy: its `ocr_sidecars` row records their sha256 (`written_sha256`), and on a remote store the version is one the ledger records as Bunko's (`own`). A stamp alone proves nothing, since anyone who can write the file can add one (security fix 2026-10-13, §8). Any other is first published as the layer `<Vol>.pre-upgrade.mokuro`, with a `preserved` block and no `ocr_engine`, and the swap starts only once that layer has COMMITTED (§8). Today's swap keeps no copy (`upgrade.rs:545-547`); `.upgrade-originals` is only cleaned up (`:698-699`). The `edited` skip (`upgrade.rs:240-278`, called at `:403` and `:414`), `Verdict::SkippedEdited` (`:155`), the force bypass and the admin edited list are removed in M2. A layer becomes the main sidecar only when it is proven to be Bunko's own bytes the same way and its own file carries a matching `ocr_engine.id`; unstamped layers are never read or deleted. **Reader (M7):** corrections go to an `edit` layer with an `edited` block, and the main sidecar is never re-uploaded after an edit. The Bunko rule does not wait for M7, because the `pre-upgrade` layer keeps existing edits. One nullable DB column is added for the proof, `ocr_sidecars.written_sha256` (2026-10-13; it supersedes "no DB column" here and in the decision log). |
| D5 | Duplicates and case | RemoteStore behaves like a case-sensitive host. Names are made NFC on ingest; lookup is byte-exact; folding happens only at the `PathCase` edge. NFC-equal folders are merged as a union (oldest wins). NFC-equal files: the newest-created wins. **Case variants are merged automatically** (owner decision, §5.9), in line with the owner rule that the library is case-insensitive and case-preserving on every host. Every exact-name `mokuro-reader` root is part of one merged root. |
| D6 | Durability | **Sync** for reader-originated writes and the upgrade swap: invisible until COMMITTED, like a local rename. **Deferred** for Bunko's own outputs: a durable outbox, visible from STAGED. Moves and trashes carry no bytes and apply at COMMITTED (§5.9). |
| D7 | State | `index.sqlite` is a disposable cache. The outbox, ledger, submissions, conflicts, lease, instance id and local-only rows live in a durable `state.sqlite`. |
| D8 | Lost updates | Native CAS where it exists, a preflight stat elsewhere. A foreign `series.json`/`catalog.json` version is persisted as a submission in the same transaction that ingests it. A `Replace` base must be a version Bunko wrote or merged. |
| D9 | Lease | One marker name, `.mokuro-bunko.json`. The holder is the top of a total order `(epoch desc, claimed_at asc, instance_id asc)` over every fresh marker node. Freshness is judged by the provider's clock. Take over bumps the epoch. The outbox is fenced on the lease. Marker writes are not outbox ops: the lease task issues them directly, unfenced (§9.2). |
| D10 | Queue file | Same `build_document`. The cloud copy lists running volumes plus the first 100 waiting, with `truncated`, `done[]` (from COMMITTED) and `instance_id`. Progress is quantised to 0.1. Written on change, with per-provider floors and a 64 KiB cap. |
| D11 | Archive delivery | Processors keep fetching over HTTP from Bunko. Local OCR runs on a spool file. Protocol v3 and bunko-processor are unchanged. |
| D12 | Credentials | `credentials.json` at 0600, sealed with ChaCha20-Poly1305 when `MOKURO_SECRETS_KEY` is set. No OS keychain. |
| D13 | Corrupt sidecars | Report-only on remote. The startup sweep is skipped. |
| D14 | `.nocover` | A local-only row keyed by the archive's `(pid, cver)`. |
| D15 | Bunko as a WebDAV backend | Test target only; refused otherwise, because it would make two schedulers. |
| D16 | Deletes | Provider trash for anything Bunko did not write. Permanent delete only for Bunko's own ledger versions (never `echo_only` rows, §5.1), and never for a main sidecar an upgrade swap replaces (D4). |
| D17 | Microsoft redirect | `http://localhost/bunko`, port ignored. The listener binds both 127.0.0.1 and ::1. M0 registered `http://localhost`; M4 adds `http://localhost/bunko` to the registration. The path keeps Bunko's redirect apart from the reader's `http://localhost:5173` and `:5174` SPA redirects. |
| D18 | Facts ingest | Before the first compile write, ingest every `series.json`, plus `catalog.json` facts for series that have none. After that, any foreign `series.json` version, or any `series.json` at a series key with no facts row, is a submission. |
| D19 | Safety valve | Removals above 20 % of entries (in a FULL_SYNC sweep, or within 10 min in STEADY), or a root removed, renamed or moved, put the store in `Suspect`. The removals are not applied. Moves and trashes Bunko issued itself are exact ledger echoes (§5.7) and are not counted. |
| D20 | Cloud-side changes | Moves and deletes seen in the feed run the same DB hooks that DAV MOVE/DELETE run, after a tombstone grace period. Echo suppression applies only on an exact `(parent, name, cver)` match. A Bunko-issued move or trash rewrites its ledger row at COMMITTED, so its echo matches exactly and runs no hooks. |
| D21 | Events | RemoteStore emits the `WatchEvent` that inotify would, at `publish` time, and again when a version's mtime changes at COMMITTED. |
| D22 | Ordering | A metadata or status op waits until every Deferred op whose bytes it describes has COMMITTED. |
| D23 | Governor | Budgets provider cost units (Drive quota units), not requests. Background work has a per-install cap. |
| D24 | Pinned reads | Ranged reads are tied to the indexed version. Bytes that are not version-pinned never enter a cache. |
| D25 | Google project pairing | Owner decision. Every build embeds the release (`mokuro-reader-414418`, reader.mokuro.app, the default) and beta (`mokuro-reader-tan`) projects' Bunko clients. The Drive Connect step asks "Which Mokuro Reader do you use?"; headless installs pass `library connect gdrive --reader release\|beta` or `MOKURO_GOOGLE_PROJECT`. The pairing is part of the store id (§5.1). Changing it in admin runs Disconnect on the old store (drain, or Wait/Export/Discard; `released`) and Connect creates a new store (§7). The local-dev project is reachable only through `storage.library.oauth.*` overrides, which replace both embedded clients and set the pairing to `custom`. The Check step always shows the pairing and the visible volume count. |
| D26 | Reader logout | Owner decision: the reader keeps revoking on logout (reader `google-drive/token-manager.ts:345-357`). Revocation is project-wide, so it also signs Bunko out [unverified, M3]. Bunko detects `invalid_grant`, goes to `NeedsReauth`, and its banner names the likely cause. |

## 1. Goals, non-goals, configuration matrix

**Goals**
- The library lives on local disk (as today) or in the reader's `mokuro-reader/` folder on Google Drive, OneDrive, MEGA or a WebDAV server.
- The same scheduler, compiler, thumbnailer, upgrade and install code runs on either kind of store.
- Serving readers is optional.
- Readers that go straight to the cloud see Bunko's OCR progress and use the `series.json`/`catalog.json` Bunko compiles.
- M1 is a pure refactor.

**Non-goals for 0.8**
- Coordinating two Bunkos on one folder (detected and refused, D9).
- Processors talking to the cloud.
- Push channels that need a public endpoint (Drive `changes.watch`, Graph webhooks). Graph socket.io push is a later add-on [prov-onedrive B].
- Generic WebDAV clients against Bunko's own WebDAV.
- Write-back caching of reader uploads.
- Migrating a local library into a cloud one: copy it with rclone, and Bunko adopts the folder.

**Must not block:** directory-of-images volumes in the cloud, which 0.9 streaming needs. `walk_pages` (`bunko-library/src/archive/mod.rs:269-291`) runs through the shim unchanged.

**Configuration matrix**

| Storage | Serve readers | OCR placement | What runs |
|---|---|---|---|
| local | yes | local / processors / both / none | Today's server through LocalStore. Configuration (a). |
| local | no | any | (a) without `/catalog` and the reader WebDAV routes. Config only. |
| cloud | no (headless) | local / processors / both / none. Lite: processors or none (`mokuro-bunko/Cargo.toml:15`) | RemoteStore, feed, outbox, compiler, thumbnails, scheduler, status files and lease. HTTP serves admin, setup and `/_processor/*`, plus `/mokuro-reader/` archive GETs for processor tokens only. Readers use the cloud directly. Configuration (b). |
| cloud | yes (bridge) | any | Everything in the row above, plus reader WebDAV and the catalog served from the index. Readers may also use the cloud directly. Configuration (c). |

Exactly one Bunko schedules each library, enforced by the lease (§9). Processor mode is unchanged.

## 3. The LibraryStore interface

### 3.1 Sync, not async

**Why sync.**
- bunko-library is "synchronous by design: async callers use `spawn_blocking`" (`bunko-library/src/lib.rs:18`).
- bunko-dav already runs filesystem work in `spawn_blocking` (`methods/mod.rs:108`, `upload.rs:355,369`, `cache.rs:302`). So does the catalog (`catalog.rs:76`).
- The scheduler's helpers are std threads (`ocr/sched/mod.rs:474-490`).
- A sync trait keeps every call site's shape. An async trait would colour the compiler and gain nothing locally.

**How RemoteStore runs it.** RemoteStore owns a 2-worker tokio runtime and splits its methods into two kinds:

| Method kind | How it runs |
|---|---|
| Metadata | SQLite reads only. Never touches the network; safe from any thread. |
| Content and mutation | `Handle::block_on` on the store runtime. This is legal from std threads and from `spawn_blocking` threads: those carry a runtime context but are not inside an async task. tokio's own `block_on` panics inside an async task, which catches misuse. |

**Guards.**
- **Re-entry:** the store runtime's threads set a thread-local flag, and content methods `debug_assert!` it is clear. Origin hooks, `WatchEvent` sinks and submission merges (`apply_series_update` calls back into the shim) run on a dedicated `store-events` std thread, never inline on the runtime.
- **Latency classes:** inside `bunko_store::interactive(|| …)`, a content call returns `Unavailable{retry_after}` instead of waiting out a governor pause longer than 2 s. On remote, the scheduler actor issues no content calls at all (§8).

**The `afs` (tokio) shim.**
- Local or unmounted paths call `tokio::fs`.
- Remote paths run the sync op in `spawn_blocking`.
- The exception is a remote GET body, which is an async stream (§10).

### 3.2 Paths

- Paths are absolute. A mount matches by `Path::starts_with` (lexical, case-exact).
- RemoteStore stores names as NFC. `node.name_raw` keeps the provider's bytes for addressing, for example NFD names from macOS hosts.
- Lookup matches each segment **byte-exactly** against the stored NFC name. Every case and NFC equivalence stays in `PathCase::on_disk_name` (`path_case.rs:116-140`).
  - With `case_sensitive = true`, its exact fast path (`:121`) hits only the stored spelling.
  - A lowercase, NFD or case-variant request falls through to the index-backed scan and is rewritten to the stored spelling. That is the same answer an ext4 host gives.
  - When several variants match and none is exact, PathCase today takes the code-point-smallest (`variants.into_iter().min()`, `:139`). M2 adds the store hook `case_winner` (§3.3): RemoteStore answers with the §5.9 winner, and LocalStore answers `None`, so it keeps `min()`.
- `caps().case_sensitive` is `true` on RemoteStore (D5). On remote, PathCase takes this from caps and skips the startup probe (`path_case.rs:86`), which stays for LocalStore.

### 3.4 Shim routing (`bunko_store::fs::*`, `bunko_store::afs::*`)

- **No mount covers the path:** call std or tokio directly.
- **`rename(from, to)`:**
  - From an unmounted path into a store, or from a staged file to a published path in the same store: `publish` with the default intent (`Replace{base: None}`, `Admin`, `Sync`).
  - Between two published entries: move by id. If `to` holds a different entry, the move and the trashing of the old destination form one journal group. Otherwise Drive and MEGA would create a duplicate, and Graph would return 409.
  - Any other combination: `CrossesDevices`. `move_into_place` already falls back on that error (`ocr/collect.rs:206-222`).
- **`copy(from, to)` into a store:** creates `to` as a local staging file, so the rename that follows publishes it (`upgrade.rs:571`, `write.rs:593`).
- **`fs::write(final)`:** one Sync publish through a staging file.
- **`create_dir_all`:** Sync and idempotent. It makes network calls only for segments the index does not have.
- **A final name opened with `File::create`/`open_with` and never published:** stays local-only. There is no publish-on-drop, so no error is swallowed. The only intended case is `.nocover` (D14).

### 3.5 Error model

Errors stay `io::Error`, so existing `ErrorKind` checks keep working. RemoteStore wraps a `StoreError` in `io::Error::other`, and `bunko_store::classify` maps it:

| Class | Raised on | Bridge answer | Scheduler reaction |
|---|---|---|---|
| NotFound / AlreadyExists | | as today | |
| Conflict | a precondition failure; a 409/412 from the provider | 412 | origin handler (§5.7) |
| Unavailable{retry_after} | outage, throttling, an interactive call during a pause | 503 + Retry-After | hold `storage-offline` |
| NeedsAuth | expired or revoked credentials | 503 (never 401: the reader would blame its own login) | hold `storage-auth` |
| StorageFull | out of space | 507 | hold `storage-full` |
| TransferQuota | MEGA download quota | 503 + Retry-After | hold `transfer-quota` |
| LeaseHeld | standby (§9.2) | 503, `storage-lease` | no claims |
| InvalidName | provider-forbidden characters | 400 with a reason | per-volume `storage-conflict` |

LocalStore returns only std errors.

## 4. LocalStore (M1)

LocalStore forwards every call to std. No behaviour changes.

## 5. RemoteStore

### 5.1 Index and state

Each store lives in `<base>/cloud/<store-id>/`, where `store-id = sha256(provider‖pairing‖account_id‖folder)[..16]`. `pairing` is the Google pairing (`release`, `beta`, or `custom:<client_id>` when overrides are set, using the Desktop override's id, else the device override's, §7) and is empty for other providers. A different pairing or override client is therefore a different store: its outbox, ledger, submissions and conflicts never carry over.

**Rebuild rule:**
- A rebuild deletes `index.sqlite`, `blobs/` and `spool/` only.
- `state.sqlite`, `outbox/` and `submissions/` survive a resync, an index rebuild and a restart.

### 5.2 Effective mtime (D3)

**Formula:** `mtime_ns = trunc_G(base) + (H(pid ‖ cver) mod G)`.

| Provider | `base` = the field the reader lists | G |
|---|---|---|
| Drive | `modifiedTime` (`drive-files-cache.ts:240`) | 1 ms |
| OneDrive | top-level `lastModifiedDateTime` (`onedrive-provider.ts:242`), not `fileSystemInfo` | 1 s |
| MEGA | node `ts` (`mega-provider.ts:708-709`), not the fingerprint mtime | 1 s |
| WebDAV | `getlastmodified` | 1 s |

**Why it must be the listed field:** the reader treats a sidecar or cover as stale when the listed size differs or the listed `int(mtime)` exceeds the stamp in `series.json` (`metadata/cloud-sidecar-stamps.ts:193-216`). The salt is smaller than G, so `int(mtime)` equals the listed seconds. A Bunko-compiled stamp therefore never looks stale.

**Properties:**
- Deterministic per content version, and stable across index rebuilds. `Stamp`, the `series_entry_cache` keys and the ETags survive a resync.
- f64 `py_mtime` resolves about 238 ns at the current epoch, so two same-size versions within one second collide with probability about 1/4M.

**Special cases:**
- **Pending Deferred writes:** local `now` plus the salt of the sha256. The value changes once, at COMMITTED, and D21 emits an event for it.
- **Folders:** `mtime_ns` is bumped to `max(prev + 1 µs, now)` on any child add, remove or rename, so folder ETags change as a local directory's would [inv-dav "Validators"].

### 5.3 Change feeds

**Engine order:** INIT → LOCATE_ROOTS → resume cursor or FULL_SYNC → `Rescan` → INGEST_FACTS (first adoption only, §9.4) → CLAIM_LEASE → replay the Deferred outbox → STEADY. A lost cursor or a failed integrity check returns the engine to FULL_SYNC.

**FULL_SYNC (mark and sweep)**
1. Take the cursor *before* enumerating.
2. Upsert every enumerated node with `seen_gen = gen`.
3. Outbox commits during the sync stamp the current `gen`.
4. Only after a **complete** enumeration, sweep older-`gen` nodes, children first. The sweep skips nodes with a ledger entry newer than the sync start and nodes with a `pending_op`. D19 applies.
5. Emit the diffs, then `Rescan`.

**STEADY**
- **Batches:** each batch and its new cursor apply in **one transaction**, together with any submission rows it creates. Delivery is at least once, idempotent by pid.
- **Echoes:** a node equal to its ledger row on `(parent_pid, name, cver)` is our own echo. Its metadata is updated, no event is emitted (D21 already did), and no hooks run. The delete of a node whose ledger row is marked `trashed` is our own echo too. Bunko's own moves (bridge MOVE, case merge) and trashes rewrite the ledger row at COMMITTED (§5.7), so their echoes match exactly: no hooks run a second time and nothing counts toward D19. The same cver at a different parent or name, with no such rewrite, is a foreign move.
- **A ledger echo for a node absent from the index** is upserted and emits `Added`.
- **Diffing into events:**

  | Change | Event |
  |---|---|
  | create | `Added` |
  | delete | `Removed`; the hooks wait for the tombstone (§5.4) |
  | move | `Removed` + `Added`, plus move hooks |
  | content change | `Added` (what a local tmp+rename produces) |
  | foreign `series.json` / `catalog.json` | also a persisted submission (§9.3); new, because the local watcher drops `.json` |

- **Batch edges:** deletes inside a batch are deferred to its end, so MEGA moves fold correctly. A folder that moves into the subtree triggers a listing of that folder.
- **Root changes:** a root removed, renamed or moved out of its parent goes to `Suspect`. The admin chooses: follow it, or re-locate by name.
- **D19 in STEADY:** applies over a rolling 10-minute window of applied removals. Ledger-matched echoes of Bunko's own moves and trashes (case-merge journal groups included) are not counted. `Suspect` is left when the admin confirms, or when two consecutive full re-lists agree.
- **Startup:** always emits `Rescan`, so events lost between commit and delivery are recovered from SQLite.

### 5.4 Changes made directly in the cloud (D20)

In configuration (b), every rename, move and delete happens out-of-band. Today the path-keyed DB is kept right only by the DAV hooks (`bunko-dav/src/hooks.rs:41-66`, called from `methods/write.rs:629-660`). On remote, a server-side adapter replays those hooks from the feed.

**Moves:** same pid, new parent or name. They apply immediately:
- `.cbz`: `rename_volume_upload`.
- Folder: `rename_volume_upload` per `.cbz` under it (from the index), then `rename_ocr_sidecars_under_prefix` and `rename_volume_uuids_under_prefix`.
- Then `archives_removed` for the old paths and `archive_arrived` for the new ones.

**Deletes:** a tombstone is written. Removal effects run when it expires, after max(2 × feed interval, `quiet_s` = 120 s):
- `.cbz`: `forget_volume_upload`, `forget_volume_uuid`, `forget_ocr_sidecars_of_volume`, `archives_removed`.
- Folder: the `*_under_prefix` forgets.
- `.mokuro`: `primary_sidecar_leaving` (bytes from the blob cache when cached), then `forget_ocr_sidecar`.
- A re-appearance of the same pid inside the window is a move. That covers a MEGA delete+create spanning two `sc` batches.

**Content changes:** a foreign new version (cver not in the ledger) of a `.mokuro`, `.mokuro.gz` or `.<layer>.mokuro` runs `forget_ocr_sidecar` for its path at once, as a DAV PUT does (`bunko-dav/src/methods/put.rs:305`, `methods/mod.rs:247-257`). Otherwise `classify` reads the old row first (`upgrade.rs:88-101`) and would judge a reader-overwritten main sidecar current.

**Quiet period:** `recently_removed(p)` reports tombstones younger than `quiet_s`. On remote, a claim skips a volume whose primary or layer sidecar vanished inside that window while its `.cbz` remained. This covers the reader's MEGA replace, which permanently deletes every same-name copy and then uploads (`mega-provider.ts:778-795`).

**Series facts:** a `series.json` arriving at a series key that has no facts row is ingested as a submission (D18). A reader's folder rename therefore carries its facts, even though that file's `(pid, cver)` is Bunko's own.

### 5.5 Small-file cache

- **What:** files of 4 MiB or less: `.mokuro`, `.mokuro.gz`, `.<layer>.mokuro`, covers, `series.json`, `catalog.json`, control files, and the linked user's root JSON.
- **Storage:** content-addressed blobs. A blob is fresh iff `cached.cver == node.cver`, so the feed is the invalidator. The blob's sha256 is what `content_sha256` returns. It is used by `same_bytes`, by own-version capture (§5.7) and by the case-merge identical-file check (§5.9).
- **Revalidation:** a read inside a read-modify-write, and every linked-user read, first makes one conditional call: Drive `files.get fields=md5Checksum,version,headRevisionId`, Graph or WebDAV `If-None-Match`, MEGA node `g`.
- **Eviction and pins:** LRU within `cache_mb` (default 1024). Outbox and submission bytes are durable copies in `state/`, not cache entries.
- **Hash check:** the provider hash is verified on fill wherever the provider supplies one.

### 5.6 Archive access

**Central directory.** The first `open` of a `.cbz` version does the following:
1. Reads the last `min(size, 256 KiB)` bytes.
2. Parses them with the existing `read_central_directory`.
3. Stores the result in `zipdir`.

After that, page counts (`owed.rs:201`, `compiler.rs:139`), covers and manifests cost one ranged GET per member. `compile_volume` always reads page names (`compiler.rs:139`), so a first sync costs about one or two ranged GETs plus one sidecar download per volume, at background priority under the D23 cap.

**Pinned reads (D24).**

| Provider | How a read is pinned to the indexed version |
|---|---|
| Drive | `files/{id}/revisions/{headRevisionId}?alt=media` with Range [unverified under `drive.file`, M3]. Fallback: re-stat `headRevisionId` after the read. |
| WebDAV | `If-Match: <strong getetag>` on every GET. A weak or missing ETag means a re-PROPFIND after the read. |
| Graph | Compare the response's ETag/cTag header with the expected cver [unverified, M4]. Fallback: re-stat after the read. |
| MEGA | Inherent: a new version is a new handle. |

On a mismatch the bytes are dropped and the index is refreshed. Nothing enters `zipdir`, the block cache or the spool before its pin check passes.

**Progressive spool, single egress.**
- A read run from offset 0 that has proven sequential (4 contiguous reads spanning 4 MiB), or a `local_path` call, starts a download into `spool/<pid>-<cver>.part`. One read at 0 (a magic sniff) never does. Ranged reads fetch only the blocks they cover; only a proven sequential run reads ahead (doubling, up to 4 MiB).
- Covers on a cloud library are read through `zipdir` (central directory plus one member), not the `zip` crate, which reads every member's local header while opening an archive.
- Concurrent readers block until their bytes are filled. A seek beyond `filled + 4 MiB` uses pinned ranged reads.
- One cloud download therefore serves local OCR, processor fetches (which resume with If-Range, `bunko-processor/src/fetch.rs:848-891`) and repeated bridge GETs.

**Verification.**
- On completion: check the size, then the provider hash (Drive sha256/md5, OneDrive QuickXor computed locally, Nextcloud `oc:checksums`, MEGA condensed MAC).
- Check the HTTP status and byte count first, because MEGA can serve an over-quota error body (mega-rs #16).
- A 200 reply to a Range request (OneDrive "may") has its bytes skipped up to the offset.

**Budget.**
- `spool_gb` defaults to 4 and must be at least `2 × lanes × largest archive`. `doctor` warns when it is smaller.
- Claims and prefetches are admitted against the free budget. A claim that does not fit waits in `spooling` (shown as `queued`).
- Bridge GETs fall back to pinned passthrough when the spool is full.
- Pins are held by claims, open readers and `LocalPath`.
- A bridge `.cbz` PUT moves its staged file into `spool(pid, cver)` at COMMITTED, so the OCR that follows does not download it again.

### 5.7 Write path (D6, D7, D8, D22)

**Outbox states** (in `state.sqlite`)
1. **PREPARED:** resolve the destination and record `base_cver`. For `Origin::Compiler`, the base must be own (ledger) or an applied submission; otherwise `Conflict`. Pre-allocate an id (Drive `generateIds`) or an idempotency key.
2. **STAGED:** move or copy the bytes into `outbox/<op>`, fsync, and compute sha256 (plus md5 for Drive and QuickXor for OneDrive). Commit the row. The data now survives a crash.
   - Deferred ops get a `pending_op` index row with `own=1` (read-after-write) and emit their `WatchEvent` now (D21).
   - Sync ops get no index row: other readers keep seeing the old version until COMMITTED, as with a local rename (`a_get_during_an_upload_sees_the_old_file…`, bunko-dav `tests/uploads.rs`).
3. **HELD:** waits while the lease is not ours (§9.2), or while `depends_on` ops are uncommitted (D22). A Compiler op for series S waits for every non-Compiler Deferred op under S; `catalog.json` waits for every `series.json` op.
4. **PREFLIGHT:** stat by pid, or list the parent for creates. Any of the following goes to CONFLICT:
   - `cver ≠ base`;
   - a create finds an existing name;
   - the parent pid is gone or trashed (never recreate a missing parent; the compiler's "never resurrect" rule, `service.rs:292-295`, holds across replay).
5. **UPLOADING:** use the native precondition where one exists. Persist the resumable session URL and offset before the first chunk.
6. **COMMITTED:** in **one transaction**, upsert the node, add `ledger(pid, cver, parent, name, sha256)`, and move the bytes into the blob cache (or spool, for archives). Emit `Added` for Sync ops, or for a changed mtime (D21).
   - A Bunko-issued `update` (move or rename) or `trash` commits the same way: it rewrites that pid's ledger row to the new `(parent_pid, name)`, or marks it `trashed`, in the COMMITTED transaction. On WebDAV, where the path is the id, the row moves to the new pid with the returned cver, or, when the MOVE response carries none, the cver from a PROPFIND of the destination in the same step. A file Bunko did not write gets an `echo_only` row (§5.1). Its feed echo then matches exactly: no hooks run and it does not count toward D19. The DB hooks for the move or trash run once, from this transaction's caller.
7. **SUPERSEDE_OLD** (MEGA replaces only): trash or permanently delete the previous node (D16). An upgrade swap always trashes it (D4). Replayed at startup.
8. **CONFIRMED:** the feed echo is seen. Delete the outbox file.

**Sync vs Deferred.**
- A Sync write blocks the caller through COMMITTED and returns any error.
- A Deferred write returns `Published{op}` after STAGED.

**Coalescing.** Status files and Compiler ops coalesce by destination, so only the latest is kept. An op whose base is Bunko's own previous version is rebased onto the last own committed cver of that destination. It never conflicts with itself.

**Conflict handlers, by origin**

| Origin | Handler |
|---|---|
| Compiler | Ingest the current foreign version as a submission (§9.3), recompile, retry (at most 3 per pass). A vanished target is retried after `quiet_s`. |
| Ocr (`CreateNew`) | On remote, a foreign sidecar at the name means **Discard** (audit `discarded: a sidecar appeared in the cloud`) and the pending row rolls back. There is no `_n` orphan the reader would never match. Local keeps `unique_path` (`collect.rs:183-203`). |
| Thumbs (`CreateNew`) | Drop ours; keep the reader's cover. |
| Upgrade | The main sidecar changed between judge and swap: re-judge at the next census. The `pre-upgrade` layer already committed for the old version stays. If the newer version is still outdated and unstamped, it gets its own `pre-upgrade-2` layer before its swap (D4). |
| Dav | 412 to the client. |

**Lost-update protection per provider**

| Provider | Create-exclusive | Overwrite CAS | Remaining window |
|---|---|---|---|
| OneDrive | `conflictBehavior=fail` | `If-Match: <cTag>` on `createUploadSession`, PATCH and DELETE. Small replaces also use a one-fragment session, because `If-Match` on a simple PUT is undocumented [prov-onedrive A]. | none |
| WebDAV | `If-None-Match: *` if the probe shows it is honoured | `If-Match` if probed (a wrong tag must give 412) | without both: last-writer-wins plus a re-PROPFIND, documented |
| Drive | `generateIds` (idempotent, not name-exclusive) | preflight `files.get` (5 units), then `PATCH /upload/…/{id}` (keeps the id) | about one RTT |
| MEGA | none | drain pending `sc`, then re-check the handle | about one RTT |

A foreign `series.json`/`catalog.json` version is captured as a persisted submission before Bunko may replace it (D8). A foreign write is therefore lost only if it lands inside the one-RTT window on Drive or MEGA. Detection through Drive `revisions.list` is an M3 spike [unverified].

**Own-version capture.** A committed version counts as own only in one of two cases:
- The provider returned the new version token in the write response.
- A follow-up read's hash (the provider hash, or a GET for files ≤ 4 MiB) equals the staged sha256.

Otherwise it stays unowned and goes through the foreign path. This covers WebDAV PUT responses that carry no ETag.

**Replace semantics**

| Provider | Replace |
|---|---|
| Drive | `PATCH` by id, `keepRevisionForever=false`. Unchanged bytes are never rewritten (`write_if_changed`). |
| OneDrive | An upload session on the item id. Whether the id survives is [unverified] (M4). |
| MEGA | Upload under the final name, then SUPERSEDE_OLD. A brief duplicate is resolved by newest-created-wins, and the file is never missing. prov-mega's rename dance would add a missing-file window. |
| WebDAV | PUT with `If-Match`. Without CAS: PUT to `.<name>.bunko-<op>.tmp`, then `MOVE Overwrite: T`. |

**Large uploads:**
- Drive: resumable, 8 MiB chunks; a session lasts a week.
- Graph: 32 × 320 KiB fragments.
- Nextcloud: chunking v2 above 64 MiB.
- MEGA: chunked uploads (bunko-mega).
- Bodies stream from the staged file.

**Idempotent retry after an uncertain outcome:**
- Drive: stat `prealloc_id`.
- Graph: `GET uploadUrl` for `nextExpectedRanges`.
- WebDAV: PROPFIND and compare size and hash.
- MEGA: list the parent and match name, size and fingerprint.

**Barrier.** A Sync MOVE or DELETE on path P first waits for Deferred ops under P (30 s, then 503). On WebDAV, ops pending under P are rebased; id-addressed providers need no rebase.

**Retries.**
- Exponential backoff with jitter. `Retry-After` is honoured globally.
- Attempts and age count only while health is `Online`.
- **FAILED** is reserved for permanent errors: `InvalidName`, `TooLarge`, and non-retryable 4xx after a re-stat. A FAILED op rolls back its `pending_op` row, so the volume is owed again or held with `storage-conflict`. It keeps its bytes for an admin retry or export, and records a `failed-op` conflict. Nothing is ever auto-deleted.

### 5.8 Consistency with a reader writing the same folder

| File | Rule |
|---|---|
| `.cbz` | Bunko writes one only on a bridge PUT: `Replace{base: the client's If-Match}`, or `CreateNew` for `If-None-Match: *`. On WebDAV, a `.cbz` is claimable only once two polls agree on its ETag and size, because in-place PUTs can be listed mid-write. |
| `.mokuro`, `.<layer>.mokuro` (install) | `CreateNew`, Deferred. A foreign file at the name means Discard on remote (§5.7). The quiet period (§5.4) covers delete-then-upload. |
| Bare `.mokuro` (upgrade swap) | `Replace{base: cver judged}`, Sync. An outdated main sidecar in a family listed in `ocr.upgrade.replace` is upgraded (D4). One without Bunko's `ocr_engine` stamp is first published as `<Vol>.pre-upgrade.mokuro` (`CreateNew`, Sync), and the swap waits for that layer's COMMITTED. A node the swap replaces goes to the provider trash, never a permanent delete. Unstamped layers are never read or deleted. |
| Covers | `CreateNew`. `.nocover` is a local row anchored to the archive's `(pid, cver)`, so a new archive version clears it (D14). |
| `series.json` | A foreign version becomes a persisted submission (§9.3), then a CAS write. |
| `catalog.json` | Derived. A foreign version triggers a recompile and overwrite. Adoption is the exception (D18). |
| `volume-data.json`, `profiles.json`, `goals.json` | Never merged by Bunko. Passed through only for the linked user (§10). |
| Control files | Bunko-owned. Plain replace; old versions are deleted permanently. |

Other rules:
- A cloud `.cbz` that disappears cancels its jobs once its tombstone expires, and leaves its sidecars alone.
- Bunko never deletes a file in reaction to a feed event. The one exception is the automatic case merge (§5.9). It only moves things to the provider trash: a loser copy identical to the winner's; a loser cover, `series.json` or outdated main sidecar that the merge has superseded, ingested or preserved; or an emptied losing folder.
- The corrupt-sidecar sweep is report-only on remote (D13; `thumbs/mod.rs:363-389`).

### 5.9 Duplicates, case collisions and roots (D5)

**Roots.**
- Every folder named exactly `mokuro-reader` that the reader would use forms one merged root:
  - MEGA: any non-rubbish folder with that exact name, not a case-folded match (`mega-provider.ts:644-692`).
  - Drive: any visible non-trashed folder with that name (the reader keys by name, `drive-files-cache.ts:192-196`).
  - OneDrive: `/me/drive/root:/mokuro-reader`.
  - WebDAV: `<url>/mokuro-reader/`.
- Control files and new top-level folders go into the oldest root.
- A `mokuro-reader` nested inside another is reported as a `nested-root` conflict and is not indexed as a root.

**NFC-equal folders** (Drive and MEGA duplicates, racing reader tabs) form one entry whose children are the union.
- The winner, which is both the target for new children and the display spelling, is the oldest `created_ms`, then the smallest pid. This matches the reader (`google-drive-provider.ts:1075-1085`).
- Bunko never merges them itself; the reader's FolderDeduplicator does.
- A rename or delete applies to every member.

**NFC-equal files:** the newest server-assigned `created_ms` wins, then the smallest pid. The client-settable mtime is not used. The others are `role=2`: hidden, listed in `conflict`, never auto-deleted. A DELETE trashes the whole group.

**Case variants** (`Kingdom/` beside `kingdom/`, or `Vol 1.cbz` beside `vol 1.cbz`) can appear on Drive, MEGA and case-sensitive WebDAV hosts, but not on OneDrive [prov-onedrive E].

**Before a merge.** The variants are distinct index entries, as on an ext4 host today (`bunko-server/tests/library_compile.rs:405-435`). New requests fold to one existing spelling at the edge (`path_case.rs:116-140`), so Bunko itself never creates a variant.

**The merge (owner decision).** Bunko merges case variants automatically.
- **Winner:** the oldest `created_ms`, then the smallest pid. The existing spelling wins, which is the owner rule.
  - An entry with several members (NFC-equal folders, above) has its oldest member's age. The move target is that oldest member node, the same folder the reader picks (`google-drive-provider.ts:1075-1085`).
  - PathCase returns the exact spelling when it exists (`path_case.rs:121-123, 132-134`), else the code-point-smallest variant (`min()` at `:139`). On RemoteStore, M2 replaces that `min()` with the store hook `case_winner(parent, fold)` (§3.3), which answers the winner above from the index. LocalStore keeps `min()`.
  - Requests that need folding therefore resolve to the winner. A request that spells a loser exactly (a reader uploading into `kingdom/`) still lands in the loser until the merge. Such a write resets the loser's quiet period below.
- **When:** all of these must hold:
  - Bunko holds the lease, health is `Online`, and the store is not `Suspect`;
  - the engine is in STEADY, after a complete FULL_SYNC and INGEST_FACTS;
  - neither variant has had a new node, a new version or a pending op for `quiet_s`, so a reader that is still uploading into one is left alone;
  - no OCR claim is running or spooling, and no upgrade is being judged or swapped, for any volume under either variant;
  - and, while a merge journal group is open, the scheduler claims no volume under either variant and the upgrade census skips them.
- **Plan:** built from a direct `list_dir` of every member node of both entries, never from the index alone. The merge takes the §5.7 barrier on both paths. On WebDAV it rebases ops still pending under the loser's path onto the winner.
- **Volume groups:** children merge as volume groups: `<stem>.cbz` with its `<stem>.mokuro`, `<stem>.<layer>.mokuro` and `<stem>.webp`. A group moves, dedups or blocks as a whole. Groups pair across the two folders by folded stem (`fold_name`); when the stems differ only in case, the loser's files take the winner's spelling as they move. Every child of every member node of the losing entry is planned into the winner's target node and moves there by id (Drive and MEGA `update` of the parent, WebDAV MOVE), unless the rules below trash it or block it:
  - a group or file only the loser has moves in;
  - folder and folder: merged the same way, recursively;
  - identical archives (comparison below): the winner's archive is kept and the loser's goes to the provider trash. A sidecar or layer only the loser has moves in under the winner's stem; an identical one is trashed. An unstamped layer (`edit`, `pre-upgrade*`) whose id the winner already uses with different content moves in under the next free id (`-2`, `-3`). The loser's cover is trashed when the winner has one, and its `.nocover` row is dropped;
  - differing main sidecars beside identical archives: the one whose recipe matches the primary's output-affecting recipe (`Recipe::matches`, as `verdict` checks at `upgrade.rs:396-398`) is kept. `Verdict::Current` is not used for this, because it is also returned when the upgrade is disabled and for `unknown` or unlisted families (`upgrade.rs:389-398`). The other is treated like a swap's old file (D4): if it lacks Bunko's stamp it is first kept as the winner's `pre-upgrade` layer (committed before anything is trashed), then it is trashed. If `ocr.upgrade.enabled` is off, or neither or both match, the group is blocked;
  - differing archives, a same-id layer with different content, or a file against a folder: the whole group stays in the loser, and a `case-merge-blocked` conflict lists both paths for the admin;
  - the loser's `series.json` is ingested as a submission into the winner's series key (§9.3), and trashed once that submission is applied.
- **Identical:** an equal provider hash of the same kind, else equal blob sha256 (files ≤ 4 MiB). Where no comparable provider hash exists (MEGA, a WebDAV host without checksums), compare size first, then the sha256 of pinned spooled copies under the background budget. Under `TransferQuota` the merge is deferred.
- **Moves:**
  - WebDAV merge moves send `Overwrite: F`. A 412 blocks that group.
  - After each Drive or MEGA move, Bunko re-lists the winner directly. A name that now has duplicates (a reader upload raced the move) becomes a `dup-file` conflict, and nothing is trashed.
- **Finishing:** every emptied member node of the losing entry is trashed, but only after a direct `list_dir` shows it empty, with `if_cver` where the backend supports it. A Drive folder trash takes its children with it, so a non-empty listing means re-plan in the next pass. A folder that still holds blocked children stays.
- **Same-folder file variants** (`Vol 1.cbz` and `vol 1.cbz`) are volume groups with case-variant stems and follow the same rules; their moves are renames.
- **Durability:** each merge is one journal group in the outbox (origin `Admin`, durability `Deferred`). It resumes after a crash, replays only after CLAIM_LEASE, and is fenced on the lease. A move or trash has no bytes to show early, so the index applies each one at its COMMITTED.
- **Ledger and D19:** each merge move and trash rewrites its ledger row at COMMITTED (§5.7), so its feed echo is exact. Merge moves and trashes never count toward D19. If the store still becomes `Suspect` mid-merge, the merge pauses and resumes from its journal once `Suspect` is left.
- **DB hooks:** run once, at COMMITTED, per file: `rename_volume_upload` for each moved archive, plus that volume's `ocr_sidecars` and uuid rows re-keyed to the new paths (per-volume forms of `rename_ocr_sidecars_under_prefix`/`rename_volume_uuids_under_prefix`, new in M2). Trashed loser files get the removal hooks of §5.4 for their path. The folder-prefix forms (`write.rs:648-655`) are never used, because blocked children may stay behind in the loser.
- **Recreate loop:** a reader that keys folders by exact name can recreate the loser. If a loser is recreated more than 3 times in 24 h, Bunko stops merging it and records `case-merge-blocked` ("Mokuro Reader keeps recreating this folder").
- **Admin actions on `case-merge-blocked`:** "Keep this copy" / "Keep that copy". The other goes to the provider trash, through a merge journal group under the same rules.
- **Record:** every merge is audited and listed in the admin Storage panel under "Recent merges".
- **Reader effect** [unverified, checked in M2 and M7]: the reader should see a merge move as a rename, not as volumes deleted and re-added.

**Case-only rename:**
- Drive, OneDrive and MEGA: a rename by id (OneDrive is [unverified], an M4 check).
- WebDAV: a direct MOVE first. Only if the host refuses or ignores it, a journaled two-step through a temporary name [prov-webdav E].

**Other cases:**
- File and folder with the same name: the folder wins, and the file goes into `conflict`.
- NFD names are NFC-normalised on ingest and addressed with `name_raw`.

### 5.10 Crash recovery and startup

- The ingest transaction includes the cursor and the submission rows, so ingest restarts cleanly.
- Unreferenced staging, spool and blob files are swept.
- A `pending_op` row without an op is rolled back after a targeted stat.

Outbox handling at startup, in `seq` order:

| State | Sync op | Deferred op |
|---|---|---|
| PREPARED | discard | discard |
| STAGED / HELD / PREFLIGHT | discard (the client saw a failed request and retries) | resume after CLAIM_LEASE |
| UPLOADING | reconcile only: query the session or look the result up (§5.7); index it if committed, else discard | the same lookup; if committed → COMMITTED, if absent → restart after CLAIM_LEASE |
| COMMITTED / SUPERSEDE_OLD | await the echo / finish the supersede | same |

Deferred replay is gated behind CLAIM_LEASE. In standby, Deferred ops stay HELD, and admin shows "N results from before the takeover" with Apply and Discard. Queued status-file ops are dropped on lease loss. Marker writes are not outbox ops (§9.2).

### 5.11 Outages, quotas, governor (D23)

**Governor (one per backend).** A cost budget, a concurrency semaphore, and a global `pause_until` driven by `Retry-After`.
- Priority, highest first: bridge interactive (exempt from the background budget, but metered) > lease and status files > OCR spool > background (compile, thumbnails, reconcile, first-sync CD reads).
- A bridge PUT upload bypasses the background transfer semaphore. If the provider is paused for more than 60 s it gets 503 + Retry-After instead of waiting, which keeps it inside the reader's 30-min XHR timeout (`webdav-upload.ts:277-278`).

**Defaults**

| Provider | Limits |
|---|---|
| Drive | Background: 20,000 quota units/min per install; 5 req/s; 2 writes/s; 3 transfers |
| OneDrive | 8 req/s, 2 transfers, User-Agent `ISV|Mokuro|Bunko/0.8.x` |
| MEGA | 1 `cs` batch/s, 2 transfers |
| WebDAV | 3 concurrent requests |

**Drive project costs.** The limits page (updated 2026-09-11) sets 1M units/min per project, a 400M-units/day threshold with no increase, and 1 TB/day egress. It says exceeding the limits "is planned to incur charges … later in 2026" with at least 90 days' notice. Unit costs: get 5, list 100, download 200, update 50; `changes.list` is not listed [unverified, measured in M3]. Every Bunko install and every reader shares the release project. Estimates:

| Activity | Cost |
|---|---|
| Idle install (feed every 300 s at ≤100 units, heartbeat every 300 s at 50) | ≤ 43k units/day |
| First sync | about 400–600 units per volume; 5,000 volumes ≈ 2–3M units, about 2 h at the cap |
| One open reader tab polling control files (§12) | ≤ 7k units/day |
| Egress | every spool download and every bridge archive GET |

The admin panel shows per-install units and egress per hour and per day.

**Hard stops**

| Error | State | Effect |
|---|---|---|
| Drive `storageQuotaExceeded`, Graph/WebDAV 507 | `StorageFull` | writes stop, outbox kept |
| MEGA -17 | `TransferQuota` | downloads pause; re-probe at 30 min, doubling to 6 h |
| Drive `dailyLimitExceeded` | project-wide | reported as such |

**Provider unreachable.**
- Metadata and cached reads keep working (stale, with the age shown in admin).
- Archive GETs that are not spooled get 503 with Retry-After.
- Deferred writes queue.
- The scheduler holds new claims (`storage-offline`) while health is not Online, or while the outbox exceeds `outbox_hold_mb` (2048). Running jobs finish into the outbox.
- Above `outbox_max_gb` (8), Deferred writes fail with 507.

Config validation refuses a sign-in flow whose override client is missing (a device-only override cannot run the loopback flow, and the reverse).
- **Check step:** shows the pairing and "N volumes visible". When no `mokuro-reader/` is visible, "Create it?" comes with a warning: "No Mokuro Reader folder is visible with the <release/beta> pairing. If you use the other Mokuro Reader, switch the pairing." When a folder is visible but holds 10 volumes or fewer, the Check step offers to try the other pairing; that costs one more consent. M0's wrong pairing listed only 10 files, so it showed at most 10 volumes, and this threshold catches it however those files split. A genuinely small library just declines the offer.
- **Changing the pairing** in admin is a library switch: "this is a different library". It runs Disconnect on the old store (steps 1–3 below: drain, or Wait / Export / Discard; then write `released`). Connect then signs in with the new pairing's client and creates a new store, because the pairing is part of the store id (§5.1). A configured pairing that differs from the connected store's (an edited `google_project`, a changed `MOKURO_GOOGLE_PROJECT`, or changed overrides) is never applied silently at startup. Bunko keeps the old store and holds with `storage-auth` ("The Google pairing changed; disconnect the old library first"), and `doctor` names both pairings, until `library disconnect` or admin runs the Disconnect.
- The pairing appears in admin and in `doctor`.

**Storage (D12).**
- `<base>/cloud/credentials.json`, mode 0600, directory 0700 (Windows: the profile ACL), written atomically.
- Kept apart from `mokuro.db`, so DB backups carry no tokens.
- Per store: refresh token, access token and expiry, account id and label, the client id used.
- Sealed with ChaCha20-Poly1305 when `MOKURO_SECRETS_KEY` or `MOKURO_SECRETS_KEY_FILE` is set. The key must be 32 random bytes in base64 (`openssl rand -base64 32`); passphrases are refused, since a fast hash of one would be cheap to brute-force from a copy of the sealed file.
- The MEGA blob is documented as password-equivalent.
- Secrets never go into `config.yaml`, logs or admin APIs.

**Refresh and re-auth.**
- Refresh 5 min before expiry, under a per-store mutex. A rotated Microsoft refresh token is persisted **before** the new access token is used.
- Any of these sets `NeedsReauth`: `invalid_grant`, a 401 after refresh, MEGA -15, WebDAV 401/403.
- In `NeedsReauth`:
  - provider calls stop and the index keeps serving reads;
  - Deferred ops stay queued and the queue is held with `storage-auth`;
  - the marker heartbeat lapses;
  - admin and the tray say "Sign in to Google Drive again". For Google they add: "Access was removed. Signing out of Google Drive in Mokuro Reader does this, because it removes access for every Mokuro app." (D26; the reader keeps revoking by owner decision. That the revocation is project-wide is [unverified]; M3 checks it before this text ships.)
  - The banner fires once per transition; the tray notifies once.
- Reconnecting with a different account id is refused unless the admin chooses "use this account's library instead".

**Disconnect.**
1. Drain the outbox, or show the count ("37 results not yet uploaded", FAILED ops and unapplied submissions included) with Wait / Export to a folder / Discard.
   - **Export target (security fix 2026-10-13).** No HTTP API (admin, setup, the app/control API) lets the caller choose the folder: Export writes into a new folder Bunko owns, `<base>/exports/<store-id>-<UTC time>/`, and the report returns its path; a request that names a `folder` is refused. Only the local CLI (`library disconnect --export DIR`, in-process, run by the machine's user) names its own folder, refused when it exists and is not empty or is a symlink; with a server running, the CLI asks it for an ordinary Export and copies the files from Bunko's folder into DIR itself. Every file is created new (`create_new`, never through an existing file or symlink) under a flat, sanitised name `<op id>-<destination segments joined by __>` (no separators, no `..`), and `index.json` maps each file back to its destination. The store first copies the owed bytes into a fresh staging folder of Bunko's own (its destinations are checked `RelPath`s, so they stay inside it).
2. Write `state: "released"` into the marker.
3. Delete the credentials and the store directory (index, state, caches, spool). The directory is marked, and later removed, only when its name is a store id (16 lowercase hex digits), it is a real directory directly under `<base>/cloud` (not a symlink) and it resolves to a child of the resolved `<base>/cloud`; inside it, symlinks are removed themselves, never followed.

Disconnect never deletes preserved data. The copies D4 keeps are `pre-upgrade` layers in the cloud library, not in the store directory. Results that were not uploaded are removed only when the admin picks Discard in step 1. If a store directory ever holds an `.upgrade-originals/` folder, step 3 leaves it in place.

For Google, Bunko never revokes. For MEGA it kills only its own session.

## 8. OCR integration

The `ocr/**` logic runs through the shim. The deltas on remote:

**Pending detection.**
- `list_archives` (`owed.rs:132-146`), `compute`, `row_done` and the periodic walk (`sched/mod.rs:603`) are index reads.
- On remote, `archive_arrived` (`settle.rs:600-625`, dispatched on the actor at `sched/mod.rs:545`) does not run `compute`/`pages_of` inline. They go to `run_background` (`sched/mod.rs:474-490`), and the volume is inserted as "pages unknown". The actor never blocks on the network.

**Claims.**
- `stamp_of` (`types.rs:90-96`) reads `Meta`. D3 makes `(size, mtime_ns)` a faithful version pin, so `collect.rs:267`, `settle.rs:574` and `claim.rs:821` keep their meaning.
- Sync writes are invisible until COMMITTED, so a bridge PUT's pending state is never claimed with a stamp that changes later.
- `still_owed` (`claim.rs:794`) also checks `recently_removed` (§5.4).

**Local OCR on remote** (an M2 scheduler change):
1. A claim for a local session enters `spooling` (the queue file shows `queued`).
2. The store runtime materialises it with `local_path`, after spool admission (§5.6).
3. The actor then submits a `VolumeOp` whose `archive` is the spool path (`sched/session.rs:176-180` already picks the string).
4. The pin is released at settle. The next claim per lane is spooled ahead, budget permitting.
5. A version change before submit returns the claim as `differs`.

**Remote processors fetch from Bunko over HTTP, unchanged:** `GET /mokuro-reader/<rel>` with Range and If-Range against the ETag (PROTOCOL.md step 5), served from the progressive spool. Reasons:
- protocol v3 and deployed processors stay as they are;
- cloud credentials and MEGA keys stay on one machine;
- one cloud egress per claim, even across processor retries;
- one version pin from claim to install;
- MEGA needs client-side decryption, and Drive has no signed URLs.

The cost is a double hop through Bunko's link.

**Install.**
- `move_into_place(result, target, {CreateNew, Ocr{claim}, Deferred})` returns at STAGED. `Installed` is therefore reported during an outage, and `collect::run` deletes only a result that was durably handed off (`collect.rs:246-251`).
- `record_written` (`collect.rs:367`) also records `written_sha256`: the sha256 of the normalised result, hashed before it leaves the spool, so a write that lands on the destination after the move is never recorded as Bunko's.
- On remote, an existing sidecar at install time means Discard, not `_n` (§5.7).

**Generation upgrade (D4).** It applies on every store. It is a behaviour change, so it lands in M2 with its own CHANGELOG entry, not in the M1 refactor.
- **Which main sidecars.** With `ocr.upgrade.enabled` on (default off), a main sidecar whose recipe differs from the primary's is upgraded when its family is in `ocr.upgrade.replace` (defaults `mokuro-legacy` and `mokuro`, `bunko-core/src/config.rs:255-261`). A sidecar with neither `ocr_engine` nor `version` is `unknown` and is never upgraded (`upgrade.rs:393`). Stock mokuro output (a `version`, no stamp) is `mokuro-legacy`.
- **Why the `edited` skip goes.** Today the upgrade skips a main sidecar that looks edited, by mtime after `written_at` + 2 s or by a user's audit row (`edited`, `upgrade.rs:240-278`: mtime half `:245-252`, audit half `:253-277`). It is called at `:403` for the main sidecar and at `:414` for each candidate layer, and reported as `Verdict::SkippedEdited` (`:155`) unless `force` bypasses it. The rule cannot tell a reader correction from stock mokuro output. The reader rebuilds every `.mokuro` it uploads from its DB (`buildMokuroMetadata`: `version`, `title`, `title_uuid`, `volume`, `volume_uuid`, `pages`, `chars`, optional `spine_width`), with no `ocr_engine` and no edit marker. M2 removes the skip and preserves instead:
  - **Main sidecar proven to be Bunko's own bytes:** replaced, no copy. Proof: its `ocr_sidecars` row's `written_sha256` equals the sha256 of the bytes the swap replaces, and on RemoteStore the judged version is one the ledger records as Bunko's (`Meta::own()`, content-proven). Both halves matter: a DAV PUT through Bunko to a cloud library is also a ledger write (so `own` alone means "Bunko's store wrote these bytes", not "Bunko's OCR did"), and on a local library nothing pins a version. A top-level `ocr_engine` stamp proves nothing: anyone who can write the file (a reader edit, a DAV PUT, a cloud upload) can add one, and a re-upload of edited text can keep one. A row an older build wrote has no `written_sha256`, so its file is kept once.
  - **Any other main sidecar** (stock mokuro, adopted, reader-corrected, or only stamped): before the swap, the old file is published as the layer `<Vol>.pre-upgrade.mokuro` (`publish(.., {CreateNew, Upgrade, Sync})`). It gains a top-level block `"preserved": {"by": "mokuro-bunko", "reason": "generation-upgrade", "replaced_at": <ISO>, "sha256": <old file>, "replaced_by": <new ocr_engine.id>}` and carries no `ocr_engine`, so the reader treats it as a non-model layer. If the id `pre-upgrade` is taken by different content, the id is `pre-upgrade-2`, `-3` and so on. If a `pre-upgrade*` layer that preserves the same bytes (same `preserved.sha256`) already exists, as after a retried swap, no new layer is written and the swap may proceed. The swap does not start until that layer has COMMITTED; a failure means skip and retry at the next census.
  - The preserve step and the swap run under one hold of `PathWriteLocks` on the bare file and the layer path (the swap takes the bare lock today, `upgrade.rs:550-552`). The layer is built from exactly the bytes the swap replaces: on RemoteStore from a read pinned to the swap's `base` cver (D24); on LocalStore from a read under that lock, with the bare file's `(size, mtime_ns)` re-checked just before the rename, where a mismatch means skip.
  - No `ocr_sidecars` row is recorded for a `pre-upgrade` layer. The swap's `ocr_sidecar_upgraded` audit row gains `preserved_as: <layer rel>`, absent when a main sidecar proven to be Bunko's own bytes was replaced.
- **The swap** (`upgrade.rs:548-604`, install `:564-578`) is `publish(.., {Replace{base: cver at judge}, Upgrade, Sync})`. `Unavailable` means skip and retry at the next census. On remote, a node the swap replaces goes to the provider trash, never a permanent delete (MEGA's SUPERSEDE_OLD trashes even a version Bunko wrote; Drive, OneDrive and WebDAV replace in place, where the old bytes survive only in provider version history).
- **Layers.** The upgrade reads only layers that carry an `ocr_engine` stamp or have an `ocr_sidecars` row (a filter added to `layer_candidates`, `upgrade.rs:281-307`).
  - A layer is copied in as the main sidecar (`direct_replace`) only when its *own file* carries an `ocr_engine.id` matching the target recipe **and** it is proven to be Bunko's own bytes (the same proof as the main sidecar's, for the layer's path). A row alone is not enough: `classify` reads the row first (`upgrade.rs:88-101`), and reader pushes drop the stamp (reader `metadata/layer-sync.ts:58`). A stamp alone is not enough either: a forged one would make a person's file the main sidecar. The bytes proven (read once, pinned to one version on remote) are exactly the bytes installed, and the new main sidecar's row carries their sha256. This replaces the layer half of `edited` (`:414`).
  - A layer is deleted only under the existing rules: copied in, byte-identical to the new main sidecar, and written by no enabled row (`:632-647`); or a 0.7.0-beta.3 kept layer stamped `upgraded_from_primary` (`:710-801`).
  - Unstamped layers (reader edits, `pre-upgrade`) are never read or deleted.
- **Who stamps.** Bunko's generation layers and main sidecars carry `ocr_engine` (`bunko-engines/src/lib.rs:30-31`, `session.rs:192`); `generation` is added for non-primary rows (`collect.rs:325-329`, `bunko-layout/src/sidecar.rs:386-395`). Reader edit-layer pushes carry none (reader `reader/edit/layers.ts:72-79`, `servedEngineOf` `:80-86`).
- The old row is forgotten and the new one recorded by the caller, as today (`upgrade.rs:581-583`, `collect.rs:367`), with `written_sha256`.
- **Code that changes with it (M2):** remove `Verdict::SkippedEdited` (`upgrade.rs:155`), the `force` bypass (`:403`) and the admin "Upgrade anyway" action, the census `skipped_edited`/`edited_volumes` keys (`:428-456`), the `force` read and the 409 in `ocr/admin.rs:642, 661-666`, the "Upgrade anyway" button (`web/admin/admin.js:1246`), and the admin edited list (`web/admin/admin.js:1201, 1239-1244`). Update the admin hint (`web/admin/index.html:371`, "no copy is kept; files a person edited are skipped"), the module doc (`upgrade.rs:3-4`), the `UpgradeConfig` doc (`bunko-core/src/config.rs:249`) and `docs/rust-port/spec/generation-upgrade.md` (the intro L27-28, §3 item 4 and L120-121, §4 L144, §5 L172 and its Undo paragraph L194-197, L211, §6 L226 and L231-232). The tests that change are listed in §13.

**Thumbnails.**
- `needs_thumbnail` reads the index.
- `cover_image` costs a CD-cache lookup plus one pinned member read.
- `.webp` is published with `{CreateNew, Thumbs, Deferred}`. Its `Added` event (D21) is what makes the series recompile with `cover_size`/`cover_modified`, as inotify does locally (`thumbs/mod.rs:144-152` has no hook).
- On remote the loop is event-driven (it replaces the `poll_interval` walk, `thumbs:163`). The startup sweep is skipped (D13).

**Metadata compile.**
- `MetadataService` is unchanged.
- `write_if_changed` compares against cached bytes and publishes `{Replace{base}, Compiler, Deferred}`.
- D22 makes a `series.json` that references a new sidecar or cover leave only after that file has COMMITTED. The COMMITTED event recompiles it with provider-derived stamps.

**Admin stats** (`admin.rs:105-146`) and the bench sample come from index scans and a materialised archive.

## 9. Cloud status and metadata files

### 9.1 `mokuro-reader/.mokuro-queue.json`

The same `build_document` (`ocr/queue_file.rs:41-79`) with compatible additions. `parseQueueFile` ignores unknown fields and tolerates an empty `manifest` [reader §2].

```json
{"version":1,"generated_at":"2026-10-12T10:00:00Z","instance_id":"6f1c…",
 "held":null,"next_check_after":120,"pending_volumes":837,"truncated":true,
 "volumes":[{"series":"Kingdom","volume":"Kingdom 13","path":"/mokuro-reader/Kingdom/Kingdom%2013.cbz",
             "manifest":"","jobs":[{"kind":"ocr","id":"…","state":"running","eta":"…","progress":0.4}]}],
 "done":[{"series":"Kingdom","volume":"Kingdom 12","at":"…","ocr":"Kingdom/Kingdom 12.mokuro",
          "layers":[{"id":"hayai","path":"Kingdom/Kingdom 12.hayai.mokuro"}]}]}
```

- **`volumes`:** every running volume plus the first 100 waiting (`QUEUE_REPORT_LIMIT`, `sched/status.rs:21`), with `pending_volumes` and `truncated`.
- **`progress`:** quantised to 0.1. Per-page progress (`sched/status.rs:676-686`) would change the file on almost every page.
- **`done`:** the last 100 completions or 24 h, newest first. An entry is added when its sidecar op COMMITTED (D10), never at `Installed`. Cloud readers treat presence in `done[]` as the completion signal; absence from a `truncated` list means "waiting", not "done".
- **`held.reason`:** gains `storage-offline`, `storage-auth`, `storage-full`, `transfer-quota` and `storage-lease`.
- **When it is written:** only by the lease holder, as a Deferred, coalesced op. A write happens only when the document without `generated_at` and with quantised progress changes (`queue_file.rs:142` ETag rule, plus the existing 60 s ETA hysteresis).
  - Floors: WebDAV 30 s, Drive and OneDrive 60 s, MEGA 300 s.
  - Cap: 64 KiB; waiting entries are trimmed first.
  - An idle Bunko does not rewrite it; the marker shows liveness.
- **Bridge mode:** the virtual middleware keeps serving the live file at `QUEUE_FILE_PATH` and refusing writes. The cloud copy is hidden from bridge listings.

### 9.2 `mokuro-reader/.mokuro-bunko.json` (marker and lease, D9)

```json
{"version":1,"kind":"mokuro-bunko","instance_id":"6f1c…","boot_id":"a93e…","instance_name":"nas",
 "bunko_version":"0.8.0","epoch":3,"claimed_at":"…","heartbeat_at":"…","ttl_s":900,"state":"active",
 "compiles":["series.json","catalog.json"],"ocr":true,"queue":".mokuro-queue.json","took_over_from":null}
```

**Definitions.**
- **Fresh (Bunko side):** `state == "active"` and `server_now − node.modified < ttl_s`. Both values come from the provider's clock (the listing's `Date` header and the node timestamp). Bunko never sets a control file's mtime.
- **`ttl_s`:** 900 (3600 on MEGA).
- **Rank:** higher `epoch` first, then earlier `claimed_at`, then smaller `instance_id`. Clocks only break ties; both sides compute the same order from the same set.
- **Holder:** the top-ranked fresh marker.
- **Marker set:** every node named `.mokuro-bunko.json` in the merged root, shadowed duplicates included. It is read from the `node` table while `feed_ok_at` is within 2 poll intervals, and otherwise (and always during CLAIM_LEASE) from a direct `find_named` listing. It is never taken from the index winner.

**Protocol**
1. **CLAIM_LEASE:**
   - **A fresh marker with our `instance_id` and our `last_boot_id`** (a restart): resume at once and rewrite it with the new `boot_id`.
   - **A fresh marker with our `instance_id` but an unknown `boot_id`:** a cloned data folder. Treated as foreign, with a warning.
   - **A fresh foreign marker:** standby.
   - **None fresh:**
     1. Write ours with `epoch = max(seen) + 1`. Replace the existing marker node in place where the provider can (Drive PATCH by id, Graph and WebDAV PUT with If-Match where supported); otherwise create a node.
     2. Wait `max(60 s, 2 × feed interval)`.
     3. Re-list directly. Proceed only if the top-ranked fresh marker is ours, with our `boot_id`.
     4. A loser permanently deletes its own separate node.
2. **Standby (`LeaseHeld`):**
   - The index stays live. Nothing is written, and Deferred ops stay HELD.
   - Bridge writes get 503 `storage-lease`.
   - Admin and tray say "Another Bunko (nas) manages this library — last seen 3 min ago [Take over]".
   - Take over writes `epoch = holder.epoch + 1`, `took_over_from = holder`. That wins regardless of clocks.
3. **Heartbeat** (every `ttl_s/3`):
   - Evaluate the marker set first. If anything ranks above us: stop scheduling, finish in-flight uploads, start nothing new, and alert.
   - Otherwise update our node and set `lease_ok_at`. On MEGA the update is a new node, after which the previous own node is deleted permanently.
4. **Fencing:** the outbox worker starts an upload only while `lease_ok_at` is within `ttl_s/2`. After any gap (sleep, Offline, NeedsReauth) it re-evaluates first.
   - Marker writes (claim, heartbeat, takeover, release, and a loser's delete of its own node) are not outbox ops. The lease task issues them as direct Sync backend calls, unfenced, because CLAIM_LEASE must write before any lease exists. Each commits its node and ledger row in one transaction, as §5.7 COMMITTED does, so its echo is recognised.
   - The queue file (§9.1) is an outbox op and is fenced.
5. **Shutdown and disconnect:** a clean shutdown writes nothing, so an update restart does not flip readers. "Disconnect library" writes `state: "released"`.

Two Bunkos can overlap writing for at most one heartbeat plus feed lag. That is detect-and-refuse, as the owner decided, not coordination.

### 9.3 Compiled metadata

- `series.json` and `catalog.json` are byte-identical to LocalStore output; the golden tests run on RemoteStore.
- **Submissions:** a foreign `series.json` version (its `(pid, cver)` not in the ledger), or any `series.json` at a series key without a facts row, becomes a `submission` row in the feed transaction. Its bytes are pinned under `state/submissions/`.
- **Holding:** while a series has an unapplied submission, Compiler ops for it stay HELD.
- **Apply:** `apply_series_update(title, bytes, Some("cloud"))` (`service.rs:583`), the same path as a reader PUT (`runtime.rs:758-773`). Facts merge newest-stamp-wins. The series then recompiles and is published with `Replace{base: submission cver}`, which counts as merged under D8.
- **Refused** (unparsable, or no such folder): a `conflict` row. The recompile overwrites the file, and provider history keeps it.
- **Downtime:** writes made while Bunko was down are found by version at startup and merged the same way. This is the "yield on return" rule [reader §7].

### 9.4 First adoption (INGEST_FACTS, D18)

Before CLAIM_LEASE and before any compile write:
1. Every existing `series.json` is applied as a submission.
2. `catalog.json` entries for series without a `series.json` are applied as facts-only submissions.
3. Volume uuids are read from existing sidecars (`collect.rs:116-160`).

Existing main sidecars follow the D4 rule once adopted. An outdated one in a listed family is upgraded. If it lacks Bunko's `ocr_engine` stamp (stock mokuro, or a reader-corrected file), it is first kept as a `pre-upgrade` layer (§8).

### 9.5 How the reader detects Bunko-compiled metadata

- The reader tracks, per marker node, `changedAt`: the local time it first saw the node's current version (modifiedTime, eTag or handle).
- **Fresh:** `state == "active"`, `compiles` lists the file, and `now − changedAt < 2 × ttl_s`.
- **Cold start** (no history): fresh if `now − heartbeat_at < ttl_s + 5 min`.
- An unchanged marker therefore goes stale after 2 × ttl_s even while it is polled. A live Bunko changes it every `ttl_s/3`. `released` is honoured at once.
- **Effect:** `serverCompilesMetadata = reported || anyMarkerFresh`.
- **Queue trust:** queue entries are trusted only when `instance_id` names the top-ranked fresh marker.
- `series.json` itself carries no flag, which keeps byte parity.

## 10. Bridge serving

**Code reuse.**
- The DAV code runs over the shim. PROPFIND, lookup and `PathCase` are SQLite queries.
- `PropfindCache` (`cache.rs:221-430`) is invalidated from store `WatchEvent`s (an M2 hook in `library/runtime.rs`).

**Validators (D3):** file ETag `{mtime:.6}-{size}`, folder ETag from the bumped folder mtime, `getlastmodified` in whole seconds. The DAV formatting code does not change.

**GET.**
- Small files come from the blob cache, filled on a miss.
- `.cbz` files are served from the spool when present, otherwise through the `RemoteFile` stream. Range maps to pinned `backend.read`; If-Range is checked against our ETag; memory stays flat.
- In `read.rs` (M2), `into_std() == None` selects the stream branch.
- A version change mid-stream aborts the response.
- X-Accel stays local-only.

**PUT.**
1. `Staging` (`upload.rs:242`) writes a local staging file.
2. `verify_staged` (`upload.rs:524`) and `Content-Digest` run at local speed.
3. `same_bytes` compares against the cached or spooled destination.
4. `publish(.., {Replace{base: If-Match cver} | CreateNew for If-None-Match: *, Dav{user}, Sync})`.

The 201/204 response, with the new ETag and `X-Mokuro-Put: verified`, is sent only after COMMITTED. "A failed PUT leaves the old file" holds. Other readers see the old file until then. The staged archive goes into the spool (§5.6).

**MOVE, DELETE, MKCOL, COPY.**
- All Sync.
- A folder MOVE is one `update` by id. `cbz_under` (`write.rs:677`) enumerates from the index first, and the DB hooks run after COMMITTED.
- DELETE trashes the entry and its index siblings (`sidecars.rs:59`) as one journal group.
- COPY is server-side where `caps.server_copy`, else a download and an upload.

**Per-user files.**
- `users/<u>/` stays local (unmounted).
- The single `storage.library.progress_user` has `volume-data.json`, `profiles.json` and `goals.json` mapped to the cloud root through `Roots::user_file`. Reads revalidate; writes pass through with the client's If-Match. The reader merges.
- The cloud root's per-user files and the control files stay unlisted for everyone (`stray_per_user_file_in_the_library_is_not_listed`).

**Standby:** writes get 503 `storage-lease`; reads keep working.

**Latency targets** (measured at M2/M3):

| Operation | Target |
|---|---|
| PROPFIND / stat | under 50 ms |
| Small GET, cache hit / miss | under 10 ms / 0.3–1.5 s |
| Archive first byte, spooled / passthrough | local speed / 0.3–1.5 s |
| MOVE / DELETE | 0.3–2 s |

- **Main sidecar (final, replaces the earlier 2026-10-12 wording):** the main `<Vol>.mokuro` is model output; human edits belong in alternate layers whose content shows they are not model generated. Today's reader does not follow this yet: its editor re-uploads corrections as the main sidecar, rebuilt with no `ocr_engine` and no edit marker. In M2, on every store, Bunko upgrades an outdated main sidecar in a listed family: a Bunko-stamped one is replaced with no copy (amended 2026-10-13: only one proven to be Bunko's own bytes, see below), and any other is first published as a committed `<Vol>.pre-upgrade.mokuro` layer with a `preserved` block (the replaced node goes to the provider trash on remote). The `edited` skip, `Verdict::SkippedEdited`, the force bypass and the admin edited list are removed; a layer becomes the main sidecar only with its own matching `ocr_engine.id`, and unstamped layers are never read or deleted. In M7 the reader saves corrections into an `edit` layer with an `edited` block and never re-uploads the main sidecar after an edit. The Bunko rule does not wait for M7. The earlier claims that the reader already works this way and that replaced files are backed up to `.upgrade-originals` as today were wrong and are withdrawn. No `written_sha256` or other DB column is added (superseded 2026-10-13, next entry).
- **Security fix (2026-10-13), D4 proof:** a security review found that the stamp is user-writable: anyone who can write a file (a reader edit, a DAV PUT, a cloud upload) can add Bunko's top-level `ocr_engine.id`, so "Bunko-stamped" let a person's file be replaced with no copy, and a stamped layer a person uploaded become the main sidecar. **Accepted:** "replace without a copy" and "a layer as the swap source" both require proof that Bunko wrote exactly these bytes: the path's `ocr_sidecars` row records their sha256 in a new nullable column `written_sha256` (recorded at install and by the direct swap), and on a remote store the version is also `own` in the ledger. No proof means preserve, and the layer is no source. The column is additive (`ALTER TABLE` on open); a 0.5.x rollback names its columns, so its rows leave it NULL (no proof: the next upgrade keeps a copy), and the golden schema tests pin exactly this one difference.
